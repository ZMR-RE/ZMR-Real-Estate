that project's own scoped link. Never apply any migration other than this
one as part of this change.

## Production (latest applied expected: 20260929010000)

   ends at `20260929010000` and matches this checkout (`6eacdb0` + this
   file). Exactly one local-only version may appear: `20260929020000`.
   Anything else: stop.
2. Read-only preflight: run `supabase/diagnostics/void_reconcile_conflicts_readonly.sql`,
   and confirm the `financial_transactions_audit_log` trigger exists. Give the conflict count
   to the owner.
3. `supabase db push --linked --dry-run`. It must list only `20260929020000`.
4. `supabase db push --linked` (no `--include-all` needed here).
5. Post-check:
   - the trigger `financial_transactions_void_reconcile`, its function and the view exist;
   - `anon` has no privilege on the view;
   - the migration history includes `20260929020000`.

## Practice (M6's `20260930*` migrations are ALREADY applied there)
**Never use `--linked` for Practice.** In the main checkout, the CLI link (`supabase/.temp`) points at
**production**. Every Practice command uses `--db-url "$(cat <scratch file>)"`:
- the file is scratch-only with mode 600, filled by the owner through masked terminal input;
- it is never printed, never committed, and deleted after the window;
- commands run from a **fresh apply checkout that has no `supabase/.temp` link at all**.

`20260929020000` sorts **before** already-applied versions, so a plain `db push` refuses it.
`--include-all` would push **every** local-only migration in the checkout, so it may be used only
after proving that this file is the only pending one:
1. Read-only: `supabase migration list --db-url …`. Record the **complete** remote list. It is
   expected to be the versions through `20260929010000`, plus `20260930100000` and
   `20260930110000` (M6). T1's Capture migrations are not applied.
2. The apply checkout's `supabase/migrations/` equals **exactly** that remote list plus this one
   file. For the expected list, that is `6eacdb0` + this file + the two M6 files taken from
   `b2c767d` unchanged. Never include T1's Capture migrations or anything from the foundation.
3. `supabase migration list --db-url …` again. The **only** local-only version must be
   `20260929020000`, and there must be no remote-only versions. Otherwise, stop.
4. `supabase db push --db-url … --include-all --dry-run`. It must list only `20260929020000`.
5. `supabase db push --db-url … --include-all`, then the post-checks listed for production, plus

## Rollback
Apply `supabase/rollback/20260929020000_void_reconcile_safeguard_down.sql` (it changes no rows).
Then run `supabase migration repair --status reverted 20260929020000` with the target's own
connection: `--linked` only for production from its release checkout, `--db-url` for Practice.
Finally, redeploy the previous frontend.
