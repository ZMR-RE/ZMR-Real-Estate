  The statement-date variation (unknown stays unknown, entry dates only flag): sound.
The statement-date variation (unknown stays unknown, entry dates only flag): sound.
- Statement dates are stored only when the owner gives one; existing loans stay NULL.
- When no date is known, the time the figure was entered is the comparison point.
- An entry dated on or before that point is still applied and raises a "possibly covered by statement" cause. Nothing is skipped, reversed or inferred.
- Notes, all erring towards flagging:
  - existing loans' "figure entered" time is backfilled from updated_at, which payment triggers also updated, so older loans may flag a little more;
  - the cutoff uses the UTC date, so evening entries in US time can flag an entry for the following day;
  - a confirmation without a statement date clears an earlier known statement date to unknown and uses now. The effects record keeps the earlier one.

Concurrency, refusals and older pages: confirmed

- Locking: the loan is locked before the entry, including the unlinked legacy path, which now locks the property's active loan.
- Reversals use the exact recorded change, once only.
- Refusals: in the current app, a refusal records one cause plus its effect only when the cause is new, so retries don't pile up. An older page raises the refusal and keeps nothing.
- Older pages:
  - an unchanged balance resend is allowed and can't overwrite;
  - a changed balance is refused;
  - counters and statement dates can't be written by clients;
  - inserts are linked on the server;
  - voids run the same core.

Fix before the Practice test (small)

C1. Out-of-date "still active" causes.
- A cause for an entry (refused void, or "possibly covered") is closed only when that entry's void reverses.
- If the entry is later voided through a skip path (a reset since, an inactive loan, or a legacy entry), the earlier cause stays open. It still says "It was applied" or "Not voided: … still active", with the "Entry still active" badge, about an entry that is now voided.
- Fix: every successful void, whatever its outcome, resolves that entry's open refused or possibly-covered causes as voided.
- Add a test: refused void → reset → void again gives no open "still active" cause.

Recovery drafts: corrections before any approval (not Practice blockers)

R1. Re-enabling can correct a balance twice.
- While disabled, the balance guard is gone, so the pre-integrity frontend can edit balances directly. Those edits don't move the reset counters.
- After enable_draft.sql, voiding an entry applied before the disable still sees the old reset counter and reverses its change, even though a manual reset may have happened while disabled.
- Fix: the enable migration must treat the disabled period as an unknown reset, for every active loan:
  - move both reset counters and both version counters;

  - record a reset effect with reason re_enable (allowed, since migrations run as a server-side role).
- Add a test: disable → direct balance edit → enable → void a pre-disable entry gives skipped_reset_after_entry plus a cause, not a reversal.
