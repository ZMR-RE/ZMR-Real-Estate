Release blockers (must be fixed in the fixed commit)

B1. Recovery: the database rollback and migration-history reset aren't usable, as you note they're unapproved.
- supabase/rollback/…_down.sql plus migration repair --status reverted would leave the migration's columns, tables and constraint in place while history says it isn't applied. Re-applying would fail, and future exact-set checks would mislead.
- The down script also removes the activity-table audit triggers.
- Required:
  - Primary recovery is frontend-only. The pre-integrity frontend works on the new database (inserts and voids work; balance edits are refused until roll-forward); document that degraded mode.
  - Any database disable is a new reviewed forward migration to one defined state:
    - both migrations recorded as applied;
    - the new objects retained;
    - the activity audit triggers kept;
    - the frontend is the pre-integrity build.
  - Remove the "reverted" repair step, or mark it never-to-be-used. Same rule for Practice.

B2. Atomic refusal and review recording: resolving a review can clear causes the owner never saw.
- Creating a refusal or skip cause doesn't change balance_version, so a cause added after the owner opened the review is resolved by "matches my latest statement", and by any edit-path reset.
- Required: a confirmation resolves only the cause IDs it displayed. An edit-path reset must show open causes, or resolve only those it shows.
- Recording itself is otherwise correct:
  - in the current app, the refusal, its cause and "not voided" commit together;
  - older pages raise the refusal and keep nothing, which is truthful and documented.

B3. Review context is insufficient for a safe confirmation.
- Every cause: show the source entry's date, type, amount or principal, and for reset skips when the reset happened.
- Refused causes: state that the entry is still active (not voided) and what to do next.
- Otherwise a confirmation can quietly close a void the owner still intends.

B4. Historical entries after a statement reset, without inferring coverage from dates.
- Record a statement date on every reset. Today the app never sends one; default to the reset date when none is given.
- An entry dated on or before the latest statement date for that balance is applied as today and raises a review cause. Nothing is skipped automatically.
